Most teams meet the Azure SQL elastic pool when the number of databases starts to grow, typically in a SaaS application with one database per tenant. Sizing each of those databases for its own peak is expensive, and sizing them for their average makes them slow when they get busy. A pool sits between the two: the databases share a fixed amount of compute and storage, and you pay for the pool. This post covers when a pool beats single databases, how to size it, what the per-database settings guarantee, and how to scale it by hand or on a schedule.

When an Azure SQL elastic pool pays off

Microsoft's elastic pool overview describes the right workload clearly: many databases with low average utilization and infrequent spikes, with the spikes happening at different times. It also says the opposite case, several databases with persistent medium to high utilization, should not share a pool. The more databases you can put in a pool, the larger the saving, and depending on the usage pattern Microsoft says a saving is possible with as few as two S3 databases.

The billing model explains why. There is no per-database charge. You are billed for each hour the pool exists at the highest eDTU or vCore setting that applied in that hour, whatever the databases did. In the DTU model, the eDTU unit price for a pool is 1.5 times the DTU unit price for a single database, so a pool only wins if the databases need far fewer eDTUs in total than they would need as separate databases. In the vCore model, the vCore unit price is the same for pools and single databases, which makes the comparison simpler.

Microsoft's sizing estimate is the same in both models, with eDTUs or vCores as the unit:

pool_size ≈ MAX(total_dbs × avg_usage_per_db,
                concurrently_peaking_dbs × peak_usage_per_db)

Take the smallest pool size above that number, look up its price for your region on the elastic pool pricing page, and compare it with the current cost of the databases as single databases. Prices vary by region and change over time, so do this with your own numbers. If some of the candidates are intermittent single databases, the serverless vs provisioned comparison is worth reading as well, since serverless is the other common answer to idle databases.

Azure SQL elastic pool DTU vs vCore

The purchasing models page sums up the difference. DTU pools (Basic, Standard, Premium) sell a bundle of CPU, memory and IO measured in eDTUs, with an amount of storage included. vCore pools (General Purpose, Business Critical, Hyperscale) let you choose compute and storage separately, and the vCore model is where Azure Hybrid Benefit applies. In both models compute, IO and data storage are charged per pool, but backup storage is always charged per database.

For sizing, the main practical difference is how the pool reports usage. In a DTU pool, the eDTU figure is derived from several pool-level metrics and is not the sum or maximum of the databases' DTU usage, so a single database can hit its own CPU or IO limit while the pool's eDTU graph looks fine. If you are building a new pool, vCore is the model Microsoft recommends, and you can convert a pool between models online later.

Azure SQL elastic pool per database settings

A pool has three per-database properties, described in the resource limits pages for DTU pools and vCore pools. Min and max eDTUs or vCores per database are set once for the whole pool; you cannot give one database a different value. Max storage per database is set on each database individually.

  • Max per database caps how much any one database may use, if the capacity is free. It is not a guarantee. Its main use is stopping a single database from taking over the pool.
  • Min per database reserves capacity for every database, whether it is busy or not. The default is 0. Reserved capacity is not available to the active databases, and it limits how many databases fit: Microsoft's example is that a min of 2 vCores in a 20 vCore pool allows at most 10 databases.
  • Max storage per database limits the data files of that database. The size it can actually reach is the smaller of that value and the space left in the pool, and the log file is not included.

Two details are easy to miss. First, although the settings are expressed in eDTUs or vCores, they also scale the limits for data IO, log IO, buffer pool memory and worker threads. On standard-series (Gen5) hardware, a max of 0.5 vCores per database means a limit of 50 concurrent workers for each database. Second, when the pool is fully busy, each database gets an equal share of compute time, on top of whatever min you configured. Only specific values are allowed for each pool size; the CLI can list them:

az sql elastic-pool list-editions -l westeurope --edition Standard --dtu 100 \
  -o table --show-details db-min-dtu db-max-dtu db-max-size

az sql elastic-pool update -g "$RG" -s "$SERVER" -n "$POOL" \
  --db-min-capacity 0 --db-max-capacity 2

Metrics to size and watch a pool

Microsoft's article on resource management in dense elastic pools gives recommended averages for the pool-level metrics. Going above them is a sign of contention between databases.

MetricAzure Monitor nameRecommended average
avg_instance_cpu_percentsql_instance_cpu_percentBelow 70%
max_worker_percentworkers_percentBelow 80%
avg_data_io_percentphysical_data_read_percentBelow 80%
avg_log_write_percentlog_write_percentBelow 90%
avg_allocated_storage_percentallocated_data_storage_percentBelow 90%
tempdb_log_used_percenttempdb_log_used_percentBelow 50%

For history, sys.elastic_pool_resource_stats in the master database keeps one row per pool every 15 seconds for 14 days, and requires membership in dbmanager. This query rolls it up by hour, which is the resolution that matters for billing and for scheduled scaling:

SELECT DATEADD(hour, DATEDIFF(hour, 0, end_time), 0) AS hour_utc,
       AVG(avg_cpu_percent)          AS avg_cpu,
       MAX(avg_cpu_percent)          AS peak_cpu,
       MAX(avg_data_io_percent)      AS peak_data_io,
       MAX(avg_log_write_percent)    AS peak_log_write,
       MAX(max_worker_percent)       AS peak_workers,
       MAX(avg_instance_cpu_percent) AS peak_instance_cpu,
       MAX(avg_storage_percent)      AS storage_used_pct
FROM sys.elastic_pool_resource_stats
WHERE elastic_pool_name = 'my-pool'
  AND end_time > DATEADD(day, -14, SYSUTCDATETIME())
GROUP BY DATEADD(hour, DATEDIFF(hour, 0, end_time), 0)
ORDER BY hour_utc;

To estimate the "concurrently peaking databases" term of the sizing formula, look at individual databases in sys.resource_stats, also in master, which keeps five-minute rows for about 14 days. For pooled databases its percentages are relative to the per-database max, not to the pool. In Azure Monitor, the pool exposes eDTU_used and dtu_consumption_percent for DTU pools, and cpu_used and cpu_percent for vCore pools, as listed in the elastic pool metrics reference.

Storage: pool size, database max size and tempdb

A pool has a max data size, and all databases draw from it. In vCore pools you set it in 1 GB steps up to the limit for the pool size, and you pay for the max data size you set, not for what is used. In DTU pools each size includes some storage, and Standard and Premium pools can buy extra, up to the max for that size, from a fixed list of values. The pool scaling article points out a consequence: if you reduce a DTU pool's eDTUs but keep a max data size above the smaller size's included storage, you start paying for extra storage. Reduce the max data size as well if the used space allows it.

Watch allocated space as well as used space. Out-of-space errors happen when the total size of the database files reaches the pool maximum, even if part of those files is empty. The storage limits in the tables do not include tempdb or the log. tempdb is shared by every database in the pool, so a long transaction in one database can fill the tempdb log for all of them, which is why it has its own metric. Its size depends on the pool size and is listed in the same resource limits pages.

az sql elastic-pool update -g "$RG" -s "$SERVER" -n "$POOL" --max-size 500GB
az sql db update -g "$RG" -s "$SERVER" -n "$DB" --max-size 50GB

Scaling the pool and moving databases

Scaling a pool works like scaling a single database: the service prepares new compute, then switches connections over, with a brief interruption that is generally under 30 seconds. What happens during that switch, and how to make your application retry, is covered in our post on Azure SQL scaling downtime. The duration is what differs. According to the latency table in the scaling article:

  • Within Basic, Standard and General Purpose pools, latency is proportional to the number of databases.
  • To, from or within Premium and Business Critical pools, data is copied, typically at less than 1 minute per GB, counted over the space used by all databases in the pool.
  • Within Hyperscale pools it is constant, typically under 2 minutes.

With the CLI or PowerShell (Set-AzSqlElasticPool):

az sql elastic-pool update -g "$RG" -s "$SERVER" -n "$POOL" \
  --capacity 8 --db-max-capacity 4 --no-wait

az sql elastic-pool op list -g "$RG" -s "$SERVER" --elastic-pool "$POOL" \
  --query "[?state=='IN_PROGRESS'].name" -o tsv

Set-AzSqlElasticPool -ResourceGroupName $rg -ServerName $server `
  -ElasticPoolName $pool -VCore 8 -DatabaseVCoreMax 4 -AsJob

Moving a database in or out of a pool, or between pools on the same server, follows the same latency rules and also ends with dropped connections. With ALTER DATABASE or az sql db update:

-- Into a pool (or to another pool on the same server)
ALTER DATABASE [tenant42] MODIFY (SERVICE_OBJECTIVE = ELASTIC_POOL(name = [pool1]));

-- Out of the pool, back to a single database
ALTER DATABASE [tenant42] MODIFY (SERVICE_OBJECTIVE = 'GP_Gen5_2');
az sql db update -g "$RG" -s "$SERVER" -n tenant42 --elastic-pool pool1

The dense pools article adds two operational recommendations. Do not move a database out while it is the one causing the load, because the move itself adds load to the pool. And if you create new databases often, put them in a separate pool with spare capacity until you know how they behave, then move them.

Azure SQL elastic pool auto scaling on a schedule

Provisioned pools have no built-in autoscale. If the pool is busy during working hours and quiet otherwise, the usual approach is a scheduled job, an Automation runbook or a cron job with a managed identity, that runs the update command. Since billing uses the highest size in each hour, schedule changes close to hour boundaries. A minimal cron version, with placeholders for your sizes:

# /etc/cron.d/sql-pool-scale (UTC)
# Scale up before working hours, down after.
50 6 * * 1-5  root  az login --identity -o none && az sql elastic-pool update -g RG -s SERVER -n POOL --capacity BUSY_VCORES --db-max-capacity BUSY_DB_MAX -o none
5 19 * * 1-5  root  az login --identity -o none && az sql elastic-pool update -g RG -s SERVER -n POOL --capacity QUIET_VCORES --db-max-capacity QUIET_DB_MAX -o none

Set the per-database max in the same command, because the allowed values depend on the pool size. Before scaling down, check that used space fits the smaller size's max data size, and for Premium or Business Critical pools start scaling up early enough for the data copy to finish. If you would rather not maintain these jobs, Azure Autoscaler resizes elastic pools on schedules or from Azure Monitor metrics, and can change the pool DTU, max data size and per-database max capacity.

A practical next step

Run the hourly query above against an existing pool, or the same idea against sys.resource_stats for a group of candidate databases. Find the highest hourly peak and how many databases peak together, plug both into Microsoft's formula, and compare the result with what you pay now. If the quiet hours form a regular pattern, price a smaller pool for those hours too.
