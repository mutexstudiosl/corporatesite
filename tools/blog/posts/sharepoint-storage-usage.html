SharePoint storage usage tends to get attention only once the tenant is close to its limit. At that point the admin center tells you the total but not much about where it went, and the useful detail is spread across the admin center, per-site pages and PowerShell. This post covers how the quota is calculated, what happens when you go over it, and how to work down from tenant to site, library, file version and recycle bin until you know what to clean up or which limits to change.

How the tenant storage quota is calculated

All SharePoint sites in a tenant draw from one pool. Microsoft's SharePoint limits service description gives the formula for most business and enterprise plans: 1 TB plus 10 GB per licence purchased. Some plans contribute differently (frontline plans, for example, are listed with 1 TB and no per-licence amount), and Office 365 Extra File Storage add-ons are added on top. Storage is counted in binary gigabytes, so 1 GB is 1,073,741,824 bytes. The same page notes that users' OneDrive storage is not part of this pool.

Some details matter when you are reading the numbers:

  • The site recycle bins count against the total. The limits page recommends monitoring them and emptying them regularly.
  • Deleted sites waiting in the admin center's recycle bin do not count, according to Manage site storage limits.
  • The figures lag. That same page says storage usage doesn't include changes made in the last 24 to 48 hours, so a cleanup won't show up in the bar straight away.
  • A single site can hold at most 25 TB, whatever the tenant total is.

When the SharePoint storage limit is exceeded

Going over the limit doesn't stop anything immediately, but it is not a state you can stay in. The service description says that if a tenant keeps operating above its storage limit, it risks being put into read-only mode, where users may be unable to add or modify content until usage drops or more capacity is bought. To get out of read-only mode you can reduce usage, buy extra SharePoint storage (sold in 1 GB increments) or buy licences that add to the pool. After a purchase, a Confirm purchase option can lift read-only mode for up to 14 days while the new capacity is applied, and it can be used only once in a 365-day period. For the price of extra storage, check the Microsoft 365 admin center for your agreement; it varies by region and changes over time.

If you use manual site storage limits instead of the default pooled mode, an individual site can also hit its own limit before the tenant does. Site owners then see the site as full even though the tenant has space.

Built-in SharePoint storage usage reports

Active sites in the SharePoint admin center

The Active sites page shows the tenant total and the space still available in the upper right corner. The site list has a Storage used column that you can sort, there is a built-in Largest sites view, and Export on the command bar downloads the current view as CSV (Customize the SharePoint admin center site list). For most tenants this is the quickest first look.

The list has gaps. According to Manage sites in the SharePoint admin center, Teams private and shared channel sites are left out of the main list and appear through the Channel sites column of their parent team instead, and OneDrive sites are not shown at all. If the Storage used column doesn't add up to the tenant total, channel sites are worth checking first.

The SharePoint storage usage report in the Microsoft 365 admin center

Under Reports > Usage > SharePoint > Storage, the Microsoft 365 admin center has a SharePoint Storage report with total usage, quota and a usage trend that projects future growth. It refreshes every 48 to 72 hours. It works well for capacity planning and for showing management the growth curve. It doesn't tell you which site is responsible, so you still need the Active sites list or a script for that.

Storage Metrics for a single site

Inside a site, a site collection administrator can open Site settings > Site Collection Administration > Storage Metrics, or go straight to /_layouts/15/storman.aspx under the site URL. This page breaks the site down by library and list, and you can click into folders to see their sizes. It is also where a site admin can select Request more quota when manual limits are in use, as described in the Microsoft Learn page on site storage limits.

Storage Metrics is the most detailed view Microsoft provides, but it covers one site at a time and you have to click through it. It has no export, and you can't compare folders across sites or see how a folder grew over time.

SharePoint storage usage report with PowerShell

For anything repeatable, PnP PowerShell is the practical option. It needs PowerShell 7.4.0 or later, and since 9 September 2024 you have to register your own Entra ID application before you can connect; the shared multi-tenant app is no longer an option. Registration is a one-off step:

Install-Module PnP.PowerShell -Scope CurrentUser

# One-off: creates an app registration for interactive sign-in; note its client ID
Register-PnPEntraIDAppForInteractiveLogin -ApplicationName "PnP.PowerShell" -Tenant contoso.onmicrosoft.com

After that, connect with the client ID as described in the PnP authentication docs. To list sites you connect to the admin site, and Get-PnPTenantSite requires SharePoint administrator access:

$clientId = "<your-app-client-id>"
Connect-PnPOnline -Url https://contoso-admin.sharepoint.com -Interactive -ClientId $clientId

Get-PnPTenantSite |
  Sort-Object StorageUsageCurrent -Descending |
  Select-Object Url, Template,
    @{ n = 'UsedGB';  e = { [math]::Round($_.StorageUsageCurrent / 1024, 2) } },
    @{ n = 'QuotaGB'; e = { [math]::Round($_.StorageQuota / 1024, 2) } } |
  Export-Csv .\sites-by-size.csv -NoTypeInformation

StorageUsageCurrent and StorageQuota are in megabytes, which is why the script divides by 1024. Add -IncludeOneDriveSites if you also want OneDrive accounts in the list, but remember they don't count against the SharePoint pool.

Libraries inside a site

Once you know which sites are large, connect to one of them and break it down by document library with Get-PnPFolderStorageMetric. Template 101 is a document library, and leaving hidden libraries in the output is deliberate, because system libraries such as the Preservation Hold Library can be large:

Connect-PnPOnline -Url https://contoso.sharepoint.com/sites/projects -Interactive -ClientId $clientId

Get-PnPList | Where-Object { $_.BaseTemplate -eq 101 } | ForEach-Object {
  $m = Get-PnPFolderStorageMetric -List $_
  [pscustomobject]@{
    Library      = $_.Title
    Hidden       = $_.Hidden
    Files        = $m.TotalFileCount
    TotalGB      = [math]::Round($m.TotalSize / 1GB, 2)
    FileStreamGB = [math]::Round($m.TotalFileStreamSize / 1GB, 2)
    LastModified = $m.LastModified
  }
} | Sort-Object TotalGB -Descending | Format-Table -AutoSize

The cmdlet returns SharePoint's own folder storage metrics unchanged. When TotalSize is much larger than TotalFileStreamSize, version history is the first thing we look at. You can pass -FolderSiteRelativeUrl "Shared Documents/Subfolder" to measure a single folder, though walking a whole tree that way means one call per folder.

Find large files in a SharePoint library

To find large files in a SharePoint library, read the file size field for every item. Use paging on large libraries with Get-PnPListItem:

Get-PnPListItem -List "Documents" -PageSize 2000 -Fields "FileRef","File_x0020_Size","FSObjType" |
  Where-Object { $_["FSObjType"] -eq 0 } |
  Sort-Object { [int64]$_["File_x0020_Size"] } -Descending |
  Select-Object -First 50 @{ n = 'Path'; e = { $_["FileRef"] } },
    @{ n = 'SizeMB'; e = { [math]::Round([int64]$_["File_x0020_Size"] / 1MB, 1) } }

This is the size of the current version only. A 40 MB presentation that has been saved a few hundred times can use far more space than a single large video, and the file list won't show that.

SharePoint version history storage

Every version of a file is stored and counts toward the quota, and SharePoint allows up to 50,000 major versions per file. How many versions are kept depends on the version history limits, which can be set for the organization, a site or a library. New libraries inherit the organization setting unless the site overrides it. There are two modes:

  • Automatic keeps every version from the last 30 days (within a 500-version cap), then thins older versions to hourly, daily and finally weekly snapshots. Plan version storage describes the algorithm.
  • Manual keeps a fixed number of major versions, optionally with an expiry in days.

Two points often cause confusion. Changing the limits does not trim versions that already exist; those stay until you queue a trim job. Also, for items under a retention policy or eDiscovery hold, the library's version limits are ignored until the retention period ends or the hold is released, so a site under retention can keep growing even with tight limits.

The version storage usage report

To see how much space versions use on a site, generate the version storage usage report with the SharePoint Online Management Shell. It queues a background job that writes a CSV with one row per file version to a document library you choose:

Connect-SPOService -Url https://contoso-admin.sharepoint.com

$site   = "https://contoso.sharepoint.com/sites/projects"
$report = "https://contoso.sharepoint.com/sites/projects/Reports/VersionReport.csv"

New-SPOSiteFileVersionExpirationReportJob -Identity $site -ReportUrl $report

# Repeat until the JSON status is "completed"
Get-SPOSiteFileVersionExpirationReportJobProgress -Identity $site -ReportUrl $report

There is also a library-scoped version, New-SPOListFileVersionExpirationReportJob -Site $site -List "Documents" -ReportUrl $report. The report takes more than 24 hours even on small sites and a few days on large ones, and you must not edit the file while it is being written. The tutorial for analysing the report provides an Excel template and a script. If you only want to know which files carry the most version weight, a few lines are enough. Columns ending in .Compact leave the value empty when it repeats from the previous row, so the script carries it forward:

$file = $null
Import-Csv .\VersionReport.csv | ForEach-Object {
  if ($_.'FileUrl.Compact') { $file = $_.'FileUrl.Compact' }
  [pscustomobject]@{ File = $file; Size = [int64]$_.Size }
} | Group-Object File | ForEach-Object {
  [pscustomobject]@{
    File     = $_.Name
    Versions = $_.Count
    SizeMB   = [math]::Round(($_.Group | Measure-Object Size -Sum).Sum / 1MB, 1)
  }
} | Sort-Object SizeMB -Descending | Select-Object -First 25

If the result shows versions are the problem, you can set limits for the site with Set-SPOSite -Identity $site -EnableAutoExpirationVersionTrim $true and then trim existing versions with New-SPOSiteFileVersionBatchDeleteJob. Trimmed versions are deleted permanently and bypass the recycle bin, so run the what-if analysis on the report first.

Recycle bins count against the quota

Deleting files doesn't free space straight away. Deleted items go to the site recycle bin; when they are deleted from there they move to the site collection (second-stage) recycle bin, and they are removed for good 93 days after the original deletion. Both stages use quota during that time. After a large cleanup it is worth checking how much is sitting in them:

$items = @(Get-PnPRecycleBinItem -FirstStage) + @(Get-PnPRecycleBinItem -SecondStage)
$items | Group-Object ItemState | ForEach-Object {
  [pscustomobject]@{
    Stage  = $_.Name
    Items  = $_.Count
    SizeGB = [math]::Round(($_.Group | Measure-Object Size -Sum).Sum / 1GB, 2)
  }
}

Emptying the second stage is irreversible, so make sure nobody expects to restore those items first.

Why a full folder tree with sizes is hard to get

With all of the above you can see the total, the size of each site, each library, the largest current files, version weight per file and recycle bin contents. You still can't easily see the whole folder tree of a library, or of the tenant, with sizes at every level. Storage Metrics shows folders, but one site at a time, by clicking, and without export. The admin center reports stop at site level. Getting that view from PowerShell means walking every folder of every library, calling Get-PnPFolderStorageMetric for each one and storing the results somewhere so you can compare runs later. For a handful of sites a script is fine. Across a large tenant it turns into a crawler you have to maintain.

This is where Storage Observer fits. A daemon scans SharePoint document libraries and reports to a central server, which shows each folder's size split into direct contents and subtree totals, keeps a size history per folder across scans, and lists the file types that use the most space. It runs on your own infrastructure.

A practical place to start: export the Active sites list sorted by Storage used, pick the three largest sites, and run the library script above against each of them. If one library's TotalSize stands out, queue a version storage report for that site today, since it will take a day or more to finish, and check the recycle bins while you wait.
