A Traefik CrowdSec setup has two halves. CrowdSec watches what reaches your cluster and decides which IP addresses to block, and Traefik enforces those decisions on each request through a middleware. On Kubernetes both halves are installed with Helm, and the parts that need care are the log acquisition, the bouncer key and the client IP. This post walks through all of it, using the official CrowdSec Helm chart and the community bouncer plugin for Traefik. If you are coming from ingress-nginx, our post on the ingress-nginx retirement on AKS covers the move to Traefik itself; here we assume Traefik is already your ingress.

The components and how they talk to each other

The CrowdSec documentation splits the system into a few parts. The Security Engine is the open source core. Its log processor (the agent) reads logs from configured sources, parses them and runs scenarios, which are behaviour patterns such as scanning for missing paths or brute forcing a login. When a scenario triggers, the result is sent to the Local API (LAPI), which stores decisions and acts as the middleman between the log processors, the remediation components and CrowdSec's Central API. The Central API receives the alerts you share and sends back a community blocklist.

Remediation components, still often called bouncers, are what actually block traffic. They ask the LAPI whether an IP has a decision against it and react accordingly. For Traefik, the usual bouncer is the crowdsec-bouncer-traefik-plugin, a community plugin listed in the Traefik plugin catalog.

The third part is the AppSec component, CrowdSec's web application firewall. Instead of acting on logs after the fact, the bouncer forwards each HTTP request to AppSec, which evaluates it against rules (virtual patching for known vulnerabilities, generic rules, and legacy ModSecurity rules) and tells the bouncer to block or allow it. Traefik is one of the supported integrations.

On Kubernetes this gives you an agent on each node reading container logs, a LAPI deployment, an optional AppSec deployment, and Traefik pods running the plugin as a middleware that talks to the LAPI and AppSec services over the cluster network.

Installing CrowdSec with Helm on Kubernetes

The bouncer and the LAPI share a key. Generate it once and store it in two Secrets, one in each namespace, so it never appears in a values file or a Middleware manifest. This is the approach the plugin's Kubernetes example uses:

kubectl create namespace crowdsec
kubectl create namespace traefik
BOUNCER_KEY=$(openssl rand -hex 32)
kubectl -n crowdsec create secret generic crowdsec-keys \
  --from-literal=BOUNCER_KEY_traefik="$BOUNCER_KEY"
kubectl -n traefik create secret generic crowdsec-bouncer-key \
  --from-literal=BOUNCER_KEY_traefik="$BOUNCER_KEY"

The chart lives in the crowdsecurity/helm-charts repository and deploys the Security Engine and the LAPI. The values below follow the Kubernetes installation guide and the AppSec quickstart for Traefik:

# crowdsec-values.yaml
container_runtime: containerd

agent:
  acquisition:
    - namespace: traefik
      podName: traefik-*
      program: traefik
  env:
    - name: COLLECTIONS
      value: "crowdsecurity/traefik"

lapi:
  env:
    - name: BOUNCER_KEY_traefik
      valueFrom:
        secretKeyRef:
          name: crowdsec-keys
          key: BOUNCER_KEY_traefik

appsec:
  enabled: true
  acquisitions:
    - source: appsec
      listen_addr: "0.0.0.0:7422"
      path: /
      appsec_configs:
        - crowdsecurity/appsec-default
      labels:
        type: appsec
  env:
    - name: COLLECTIONS
      value: "crowdsecurity/appsec-virtual-patching crowdsecurity/appsec-generic-rules"
helm repo add crowdsec https://crowdsecurity.github.io/helm-charts
helm repo update
helm upgrade --install crowdsec crowdsec/crowdsec \
  --namespace crowdsec --values crowdsec-values.yaml
kubectl -n crowdsec wait --for=condition=Available deployment --all --timeout=5m

container_runtime tells the agent how the container log lines are wrapped. The installation guide's comment lists json or cri (docker or containerd). If it does not match your nodes, the agent cannot parse Traefik's lines. kubectl get nodes -o wide shows the runtime in the CONTAINER-RUNTIME column.

The agent.acquisition entry selects the pods whose logs CrowdSec reads, by namespace and pod name pattern, and program: traefik routes those lines to the Traefik parser. If your Traefik release has a different name or namespace, change both fields, or the agent will run without reading anything.

BOUNCER_KEY_traefik in the LAPI environment registers a bouncer with the key from the Secret, so you do not have to run cscli bouncers add by hand. The plugin example also sets DISABLE_ONLINE_API to keep a test setup from sharing signals with CrowdSec; leave that out in production if you want the community blocklist.

For anything beyond a test, pin the chart with --version and upgrade deliberately. The plugin's example warns against overriding image.tag, because each chart version ships the image it was tested with.

Traefik access logs and what CrowdSec parses

The crowdsecurity/traefik collection installs the crowdsecurity/traefik-logs parser and the crowdsecurity/base-http-scenarios collection, which holds the generic HTTP scenarios such as crawling, 404 scanning and brute force. According to the hub page, the parser supports both CLF and JSON access logs.

Traefik's access log is off by default in the Helm chart. When enabled, it writes to standard output in the common format unless you set format: json. We use JSON. Logged headers are controlled by fields.headers.defaultMode, which defaults to drop. Keep it that way and allow only User-Agent, which the scenarios use, so cookies and Authorization headers never reach your logs.

The parser source shows which fields it reads from a JSON line: the source IP comes from ClientHost and the user agent from request_User-Agent. ClientHost is the remote IP of the request, so it is only useful if the connection Traefik sees really comes from the client. We come back to that below.

The Traefik CrowdSec bouncer plugin as a Middleware

Plugins are declared in Traefik's install (static) configuration and then used from dynamic configuration, as described in Traefik's plugin documentation. With the official Traefik Helm chart, these values load the plugin, mount the bouncer key, enable JSON access logs and keep the client IP:

# traefik-values.yaml
experimental:
  plugins:
    bouncer:
      moduleName: github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin
      version: "v1.8.2"

volumes:
  - name: crowdsec-bouncer-key
    mountPath: /etc/traefik/crowdsec
    type: secret

accessLog:
  enabled: true
  format: json
  fields:
    headers:
      defaultMode: drop
      names:
        User-Agent: keep

service:
  spec:
    externalTrafficPolicy: Local

v1.8.2 is the current release in the plugin catalog as we write this. The key under experimental.plugins (here bouncer) is the name you use in the Middleware.

The Traefik CrowdSec middleware itself is a Middleware custom resource with a spec.plugin.bouncer block. This one is close to the example in the plugin repository:

apiVersion: traefik.io/v1alpha1
kind: Middleware
metadata:
  name: bouncer
  namespace: traefik
spec:
  plugin:
    bouncer:
      enabled: true
      logLevel: INFO
      crowdsecMode: stream
      crowdsecLapiScheme: http
      crowdsecLapiHost: crowdsec-service.crowdsec.svc.cluster.local:8080
      crowdsecLapiKeyFile: /etc/traefik/crowdsec/BOUNCER_KEY_traefik
      crowdsecAppsecEnabled: true
      crowdsecAppsecHost: crowdsec-appsec-service.crowdsec.svc.cluster.local:7422

The plugin README documents the options. The ones you are most likely to change are these:

  • crowdsecMode: live (the default) asks the LAPI about each new IP and caches the answer, whether it is a ban or not, for defaultDecisionSeconds (60 by default). stream keeps a local list of banned IPs and refreshes it every updateIntervalSeconds (also 60 by default). none asks the LAPI on every request without caching. alone uses the CrowdSec Central API blocklist directly, without a local LAPI. appsec skips the IP check and only runs AppSec.
  • crowdsecLapiKeyFile: the README lets you append File to secret options and pass a path instead of the value. If both are set, the file wins.
  • clientTrustedIPs: addresses that bypass the bouncer and its cache completely, for example a VPN range.
  • updateMaxFailure: what happens when the LAPI cannot be reached. With the default 0, traffic is blocked on the first failure; -1 never blocks for that reason. In live and none modes only -1 changes the behaviour.
  • crowdsecAppsecUnreachableBlock and crowdsecAppsecFailureBlock: both default to true, so if the AppSec service is down or returns something unexpected, requests are blocked.

Those last two defaults fail closed. That is a reasonable choice for a WAF, but it means the CrowdSec pods are now on the request path. Give the LAPI and AppSec deployments the same attention you give Traefik, or decide explicitly to fail open. The README also notes that some settings, including the cache, are shared by all CrowdSec middlewares in a Traefik instance, so a ban applies on every router that uses the plugin.

Attach the middleware to a standard Ingress with an annotation in <namespace>-<name>@kubernetescrd form:

metadata:
  annotations:
    traefik.ingress.kubernetes.io/router.middlewares: traefik-bouncer@kubernetescrd

If you enable safeNaming in the Kubernetes CRD provider, the separator becomes an underscore (traefik_bouncer@kubernetescrd). On an IngressRoute, list it under the route's middlewares with name and namespace. Referencing a middleware in another namespace from an IngressRoute requires allowCrossNamespace, which is false by default; the alternative is a copy of the Middleware in each application namespace.

Getting the real client IP behind the Azure load balancer

Both halves depend on the client IP. The agent bans whatever address appears in ClientHost, and the bouncer checks the address it extracts from the request. If every request seems to come from a node, scenarios will at some point ban a node address and everyone behind it.

On AKS, Microsoft's load balancer documentation states that a LoadBalancer Service does not keep the client's IP by default: the source address delivered to the pod becomes the node's private IP. To keep it, set externalTrafficPolicy: Local on the Traefik Service, as in the values above. The Kubernetes documentation on external load balancers explains the trade-off: traffic only goes to nodes that run a Traefik pod, and the load balancer does not know how many pods each node has, so spreading can be uneven.

With the load balancer directly in front of Traefik, the remote address is the client and the bouncer's defaults work. The plugin reads X-Forwarded-For, and its README notes that this is safe because Traefik's entrypoints strip forwarded headers from untrusted peers.

If there is another proxy in front (a CDN, a WAF or another load balancer that terminates HTTP), tell Traefik and the plugin which addresses to trust. On the Traefik side, that is forwardedHeaders.trustedIPs on the entrypoint, which the Helm chart exposes per port:

ports:
  websecure:
    forwardedHeaders:
      trustedIPs:
        - "<proxy-cidr-1>"
        - "<proxy-cidr-2>"

On the plugin side, set forwardedHeadersTrustedIPs to the same ranges. The README says that once it is set, the header is only read from peers in that list, and every proxy that connects directly to Traefik must be included. If your proxy puts the client address in a header other than X-Forwarded-For, name it with forwardedHeadersCustomName. Avoid forwardedHeaders.insecure; Traefik's reference says it is for tests only. After any change, look at a few access log lines and confirm that ClientHost shows public client addresses.

Testing with a manual decision

Check that the bouncer registered and that the agent is reading Traefik's logs:

kubectl -n crowdsec exec deployment/crowdsec-lapi -- cscli bouncers list
kubectl -n crowdsec exec daemonset/crowdsec-agent -- cscli metrics show acquisition parsers

Then ban your own public IP for a few minutes and request a route that uses the middleware. cscli decisions add creates a ban by default, and the reference lists the default duration as four hours, so pass a short one:

kubectl -n crowdsec exec deployment/crowdsec-lapi -- \
  cscli decisions add --ip "$MY_PUBLIC_IP" --duration 5m --reason "bouncer test"
curl -i https://app.example.com/

The plugin answers with remediationStatusCode, 403 by default. In stream mode the ban appears after the next refresh, so allow up to updateIntervalSeconds; in live mode a cached answer for your IP can last up to defaultDecisionSeconds. Remove the decision with cscli decisions delete:

kubectl -n crowdsec exec deployment/crowdsec-lapi -- \
  cscli decisions delete --ip "$MY_PUBLIC_IP"

To test AppSec, request a path that the virtual patching rules block, such as curl -i https://app.example.com/.env, which should also return 403. Running cscli metrics show appsec inside the AppSec pod shows processed and blocked requests per rule. If you test through kubectl port-forward instead of the load balancer, requests appear to come from 127.0.0.1, so that is the address to ban.

Interpreted plugin or compiled in

Traefik runs community plugins like this one in Yaegi, an embedded Go interpreter, so the bouncer's code is interpreted on every request that passes through the middleware. A Traefik issue we opened describes the higher memory and CPU use we saw with interpreted middleware, and how compiling the same code into the binary removed it; the Traefik team declined to add that build workflow to its roadmap. Our Traefork is a soft-fork that tracks upstream Traefik and compiles ModSecurity, Geoblock, RealIP, CrowdSec and Sablier into the binary. It is not affiliated with Traefik Labs.

Where to start

Start on a test cluster or a staging namespace with crowdsecMode: stream, AppSec enabled, and the middleware attached to one low-risk route. Confirm that ClientHost shows real client addresses and that the manual ban returns 403, then watch cscli decisions list and the AppSec metrics for a few days before attaching the middleware to everything. Decide on the fail-open or fail-closed settings before you go to production, since that choice decides what an outage of the CrowdSec pods looks like to your users.
