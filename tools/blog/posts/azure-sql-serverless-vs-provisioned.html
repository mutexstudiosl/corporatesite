Choosing between Azure SQL serverless vs provisioned compute usually comes up in one of two ways. Either someone is creating a new database and the portal offers both, or an existing database costs more than expected and serverless looks like an easy saving. In both cases the answer depends on the shape of the workload rather than on its size, and Microsoft documents the billing rules precisely enough to calculate it. This post goes through how each model bills, how to work out the break-even for your own database, the situations where serverless ends up costing more, and the two alternatives worth comparing: provisioned compute with scheduled scaling, and elastic pools.

How serverless compute is billed

Serverless is a compute tier of the vCore purchasing model for single databases. It is available in the General Purpose and Hyperscale service tiers on standard-series (Gen5) hardware, and not in Business Critical or the DTU model. You configure a minimum and a maximum number of vCores, and the service scales compute within that range.

The billing rule is in the serverless billing article. Every second, Azure bills the larger of CPU used and memory used, with memory converted to vCores at 3 GB per vCore. If usage is below the minimum you configured, you pay for the minimum. Written out:

billed vCores (per second) = max(min_vcores, vcores_used, min_memory_gb / 3, memory_gb_used / 3)
compute cost               = vCore unit price (per vCore-second) * sum of billed vCores over all seconds

Two parts of that formula matter more than they first appear.

The first is memory. SQL Server uses memory for the buffer pool and keeps data cached after queries finish, so a database can be billed on memory while its CPU is close to idle. The worked example in Microsoft's billing article includes an hour where the database uses one vCore and 12 GB of memory, and is billed for 4 vCores because of the memory.

The second is the minimum. While the database is online, you never pay less than the larger of the minimum vCores and the minimum memory divided by three. Microsoft's examples: with 1 minimum vCore (3 GB minimum memory) the floor is 1 vCore; with 0.5 minimum vCores (2.1 GB minimum memory) it is 0.7 vCores. The pricing calculator shows which minimum memory goes with each combination of minimum and maximum vCores.

Storage is billed the same way as in provisioned compute. Also note that Azure Hybrid Benefit and reservation discounts do not apply to serverless. If you already pay for provisioned compute with either of those, any comparison has to use your discounted provisioned price.

Azure SQL serverless auto-pause

Auto-pause is what lets serverless cost nothing for compute. According to the auto-pause and auto-resume documentation, a database pauses when, for the whole auto-pause delay, it has zero sessions and zero CPU for user workload. While paused, only storage is billed. The delay is configurable:

  • General Purpose: minimum 15 minutes, default 60, maximum 10,080 (seven days), or -1 to disable auto-pause.
  • Hyperscale: auto-pause is in preview, with a minimum and default of 60 minutes. Named replicas are not supported with auto-pause during the preview.

The delay is billed. After the last session closes, you keep paying the minimum compute until the delay ends, and Microsoft adds that pausing itself generally takes 1 to 10 minutes after the criteria are met. Resuming generally takes about a minute. The first connection to a paused database fails with error 40613 while it resumes, so applications need retry logic, which they should have anyway.

Azure SQL Hyperscale vs serverless in General Purpose

Hyperscale serverless follows the same formula, but every replica is billed separately. The primary, each HA replica and each named replica have their own minimum and their own usage, and HA replica usage appears in a separate metric, app_cpu_billed_HA_replicas. A Hyperscale serverless database with one HA replica therefore pays at least two minimums whenever it is online. Combined with the preview status of auto-pause and the 60-minute minimum delay, Hyperscale serverless is mainly a way to get automatic compute scaling rather than a way to pay nothing at night.

How provisioned compute is billed

The vCore purchasing model documentation describes it in one sentence: the provisioned compute tier bills for the amount of compute provisioned at a fixed price per hour, regardless of workload activity. A database with 8 vCores costs the same in an idle hour as in a busy one. Storage and backup storage are billed separately and in the same way for both compute tiers, so for this comparison you can usually ignore them.

Provisioned compute is eligible for Azure Hybrid Benefit and reservations in General Purpose and Business Critical. For Hyperscale, the same page explains that Azure Hybrid Benefit is not available for new databases because Hyperscale has no SQL license fee.

Azure SQL serverless vs provisioned cost: finding the break-even

Prices vary by region and change over time, so we will not quote any here. Open the Azure SQL Database pricing page for your region and tier, and note two numbers:

  • P: the provisioned price per vCore per hour, after any Hybrid Benefit or reservation discount you actually get.
  • S: the serverless price per vCore per second. Multiply by 3,600 to get S_h, the serverless price per vCore-hour.

For a provisioned database with V vCores running H hours in a month, compute costs P × V × H. For a serverless database, it costs S × B, where B is the total vCore-seconds billed. If you define A as the average billed vCores over the month (that is, B / (H × 3600)), serverless is cheaper when:

A < V × (P / S_h)

So the question becomes how many vCores, on average across every hour including nights and weekends, serverless would bill. Paused hours count as zero, idle-but-online hours count as the minimum, and busy hours count as whatever CPU or memory the database used. The ratio P / S_h comes straight from the pricing page, and it tells you what fraction of the provisioned size the serverless average has to stay below.

A rough estimate for a database with a daily pattern looks like this:

A ≈ (hours_active × avg_billed_vcores_when_active
     + hours_idle_online × minimum_billed_vcores
     + hours_paused × 0) / H

hours_idle_online ≥ number_of_idle_periods × auto_pause_delay_in_hours

Measuring it rather than guessing

If you can, move a copy of the database (or a non-production environment with a representative load) to serverless for a couple of weeks and read the app_cpu_billed metric. The monitoring documentation describes it as the amount of compute billed, in vCore-seconds; multiply it by the unit price and you have the actual compute cost. With the Azure CLI:

DB_ID=$(az sql db show -g my-rg -s my-server -n my-db --query id -o tsv)

az monitor metrics list \
  --resource "$DB_ID" \
  --metrics app_cpu_billed \
  --aggregation Total \
  --interval 1h \
  --offset 14d \
  --query "value[0].timeseries[0].data[].total" -o json \
  | jq 'map(select(. != null)) | add'

That gives total billed vCore-seconds over the last 14 days. Divide by 14 × 24 × 3600 to get A, and compare with V × (P / S_h). The hourly series is also useful on its own: hours that sit exactly at your minimum are idle hours where the database did not pause.

Moving a database between tiers is a normal update, as shown in Create and configure a serverless database:

az sql db update -g my-rg -s my-server -n my-db \
  --edition GeneralPurpose \
  --compute-model Serverless \
  --family Gen5 \
  --min-capacity 1 \
  --capacity 4 \
  --auto-pause-delay 60

Changing tier is a scaling operation like any other, with a short disconnection at the end. We cover what happens during that switch in a separate post on Azure SQL scaling downtime.

When serverless ends up more expensive

Microsoft's own guidance is that serverless suits single databases with intermittent, unpredictable usage and low average utilization, and provisioned suits regular usage with higher average utilization. In practice, these are the cases where we see serverless lose the comparison.

Steady load

If the database is busy most hours of the day, A ends up close to the provisioned size, and the comparison comes down to the two unit prices plus any provisioned discounts that serverless cannot use. A database used from early morning to late evening on weekdays may still pause at night and at weekends; one that serves a customer-facing application across time zones probably will not.

Connections and jobs that keep it awake

Auto-pause needs zero sessions for the whole delay. The documentation states that open sessions are the most common reason a serverless database does not pause. Typical sources are connection pools that keep a minimum number of idle connections, health checks that connect to the database, monitoring agents, scheduled jobs that run more often than the delay, and a query window someone left open. Auto-resume is also triggered by management operations, such as viewing auditing records, reading Query Store settings, running vulnerability assessment scans or changing tags on the database. The full list is in the auto-pause article.

To see which sessions are connected right now, Microsoft provides this query (run it, then disconnect, since your own session also blocks auto-pause):

SELECT session_id, host_name, program_name, login_name, status,
       login_time, last_request_start_time, last_request_end_time
FROM sys.dm_exec_sessions AS s
INNER JOIN sys.dm_resource_governor_workload_groups AS wg
    ON s.group_id = wg.group_id
WHERE s.session_id <> @@SPID
  AND (
        (wg.name LIKE 'UserPrimaryGroup.DB%'
         AND TRY_CAST(RIGHT(wg.name, LEN(wg.name) - LEN('UserPrimaryGroup.DB') - 2) AS int) = DB_ID())
        OR wg.name = 'DACGroup'
      );

Features that block auto-pause

Some features prevent auto-pause entirely, and the documentation recommends disabling auto-pause when you use them: active geo-replication and failover groups, long-term backup retention, a DNS alias on the logical server, the sync database in SQL Data Sync, and using the database as an elastic jobs job database. Any of these turns serverless into a database that is always online and always billed at least the minimum, at the serverless unit price and without Hybrid Benefit or reservations. Long-term retention in particular is a common compliance requirement, so check for it before anything else.

Provisioned compute with scheduled scaling

Many databases that look like serverless candidates are not intermittent at all. They are busy during working hours and quiet at night and at weekends, and the pattern repeats every week. For those, a third approach often compares well: keep provisioned compute, keep your discounts, and change the size on a schedule. Since provisioned compute is billed per hour, a database that runs at a large size for the working day and a small size for the rest costs roughly the weighted average of the two hourly prices.

The change itself is the same command you would run by hand:

az sql db update -g my-rg -s my-server -n my-db --service-objective GP_Gen5_8   # before working hours
az sql db update -g my-rg -s my-server -n my-db --service-objective GP_Gen5_2   # after working hours

Azure has no built-in setting to do this for Azure SQL, so teams usually run these commands from Azure Automation, a pipeline or a scheduled job. We built Azure Autoscaler for this case: it runs as a container in your environment and resizes Azure SQL databases and elastic pools on schedules or from Azure Monitor metrics. Whatever runs the schedule, remember that each resize ends with a brief disconnection, so schedule them outside peak use and make sure the application retries.

The difference from serverless is predictability. You choose the sizes and the times, the database never pauses, there is no resume delay on the first connection, and the bill is the same every week.

Azure SQL serverless vs elastic pool

If you have several databases, compare an elastic pool as well. Serverless is a tier for single databases. A pool is provisioned compute shared by databases on the same server: you pay for each hour the pool exists at its configured vCores or eDTUs, with no per-database charge, and in the vCore model the unit price for pools is the same as for single databases.

Pools work best when there are many databases with low average use and peaks at different times, which is common in SaaS applications with one database per tenant. Microsoft's sizing estimate for the vCore model is:

pool vCores ≈ MAX(total_dbs × avg_vcores_per_db,
                  concurrently_peaking_dbs × peak_vcores_per_db)

Take the smallest pool size above that number and compare its price with what the databases would cost individually, provisioned or serverless. Features such as geo-replication, which block auto-pause in serverless, cost nothing extra in this comparison, because nothing in a pool pauses to begin with. Databases that are busy at the same times do not share well and are better left as single databases.

A practical next step

Pick one database and pull two weeks of hourly cpu_percent from Azure Monitor. If it is already serverless, use app_cpu_billed instead. Count the hours that are effectively idle, check the database against the list of features that block auto-pause, and run the break-even formula with the unit prices for your region. If most idle hours fall in predictable blocks, also price the scheduled-scaling option. If you have a group of small databases with uneven peaks, price a pool. The cheapest option is usually obvious once you have the hourly data in front of you.
