When an Azure Blob Storage cost line goes up, the first reaction is usually to look at how much data the account holds. That is often the right place to start, but capacity is only one of the meters on the invoice. Transactions, data retrieval from cooler tiers, early deletion charges, retained versions and snapshots, and geo-replication can each move the total, and some of them grow without anyone uploading new data. This post goes through what you are billed for, how to see each part in Cost Management and Azure Monitor, and how to get the breakdown by folder or prefix that the built-in tools do not give you.

The meters behind an Azure Blob Storage cost

Microsoft's cost planning article for Blob Storage lists the meters. The ones most accounts see are data storage (per GB per month), operations (per transaction, usually priced per 10,000), data retrieval (per GB, only for the cool, cold and archive tiers) and data transfer (per GB). Others appear only when you enable a feature, such as blob index tags, SFTP (charged per hour while enabled) or blob inventory.

Unit prices depend on region, redundancy, access tier and namespace type, and they change over time, so we do not quote them here. Use the Block blob pricing page with the filters set to match your account. When you check the maths, note that the "GB" on the bill is a binary gigabyte (GiB), and capacity is billed on the average daily amount stored over the month.

Capacity per access tier

Block blobs live in one of four access tiers. The per-GB capacity price falls as the tier gets cooler, while the cost of reading and the per-transaction price rise. On general-purpose v2 accounts the cooler tiers also have a minimum retention period:

TierMinimum retentionTime to first byteReads
HotNoneMillisecondsNo per-GB retrieval charge
Cool30 daysMillisecondsPer-GB retrieval charge
Cold90 daysMillisecondsPer-GB retrieval charge
Archive180 daysHours (rehydration first)Highest retrieval cost

Archive is offline. To read a blob you rehydrate it to an online tier, which can take up to 15 hours depending on the priority you choose, and high-priority rehydration costs more. Archive is only available on LRS, GRS and RA-GRS accounts. There is also a smart tier that moves data between hot, cool and cold for a monitoring fee, without tier transition or early deletion charges.

Be careful with the account's default access tier. Blobs uploaded without an explicit tier inherit it, so changing the default from hot to cool charges a write operation for every such blob, and changing it back charges a read operation plus data retrieval for each.

Transactions and data retrieval

The pricing page lists prices per operation type (write, read, list and create container, other), usually per 10,000 operations. Microsoft has a table that maps each REST operation to its type; Delete Blob, for example, is free on general-purpose v2. Transactions cost more in cooler tiers, and reads from cool, cold and archive also pay per GB retrieved. A workload that writes many small objects, or a backup job that reads the cool tier every week, can pay more for operations and retrieval than for capacity.

Early deletion

If a blob in cool, cold or archive is deleted, overwritten or moved to another tier before its minimum period, you pay the remaining days. Microsoft's example: a blob moved to cool and deleted after 21 days is charged an extra 9 days of cool storage. Overwriting the whole object with Put Blob, Put Block List or Copy Blob counts as an early deletion too, which catches tools that rewrite files in place. With soft delete enabled, the penalty only applies once the retention period ends.

Versions, snapshots and soft delete

Versions and snapshots are billed at the same rate as live data, and so are soft-deleted objects until their retention ends. As long as nobody sets a tier explicitly, you pay for unique blocks across the base blob and its versions and snapshots. Once you set the tier of a blob, version or snapshot, you pay for the full content length of that object, and for the full length of the oldest version left in the original tier (see the versioning billing rules). This is why tiering a heavily versioned container can make capacity go up rather than down.

Soft delete has a quieter effect. On an account without versioning, every overwrite creates a soft-deleted snapshot of the previous state, and that snapshot creation is not logged. A job that rewrites the same checkpoint file every few minutes, on an account with a long retention period (up to 365 days), builds up billable data that is easy to miss. With versioning on, overwrites create previous versions instead, and those stay until something deletes them.

Redundancy and data transfer

The capacity price depends on the redundancy option. Geo-redundant accounts (GRS, RA-GRS, GZRS) also pay a per-GB geo-replication data transfer charge. Data leaving the Azure region is billed as bandwidth, which is priced on the separate bandwidth pricing page, not the storage one. Object replication to another region counts as well.

Reading the bill in Cost Management

In Cost analysis, open the Resources smart view at the subscription or resource group scope and expand the storage account row. The next level shows the account's cost by product meter, which is the Azure storage cost breakdown you want: capacity per tier, each operation type, retrieval and transfer as separate lines. In a customizable view, filter to the storage account and group by a more detailed attribute (Cost analysis groups by one attribute at a time), with granularity set to Daily so you can see the day a meter changed. For deeper analysis, the planning article recommends a scheduled cost export.

Capacity metrics in Azure Monitor

Where Cost Management shows money, Azure Monitor shows how much data sits in each tier. The Blob Storage metrics include BlobCapacity and BlobCount with Tier and BlobType dimensions. They are emitted hourly but recomputed only a few times a day, so do not expect them to react to an upload straight away. This lists capacity per tier for the last two days:

az monitor metrics list \
  --resource "/subscriptions/<sub-id>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<account>/blobServices/default" \
  --metrics BlobCapacity \
  --dimension Tier \
  --aggregation Average \
  --interval PT1H \
  --offset 2d \
  --output table

There are also container-level metrics (ContainerUsedSize and ContainerBlobCount), listed as advanced platform metrics on the same page. Two limits apply. BlobCapacity does not separate soft-deleted data from active data, and nothing in Azure Monitor goes below the container.

Blob inventory reports

Blob inventory produces a daily or weekly CSV or Parquet file listing every blob, and optionally every version, snapshot and soft-deleted object, with the properties you choose. This is the raw material for an Azure Blob Storage cost analysis at the object level. A rule that captures what you need for cost work looks like this:

{
  "enabled": true,
  "rules": [
    {
      "enabled": true,
      "name": "cost-weekly",
      "destination": "inventory",
      "definition": {
        "filters": {
          "blobTypes": ["blockBlob", "appendBlob"],
          "includeSnapshots": true,
          "includeBlobVersions": true,
          "includeDeleted": true
        },
        "format": "csv",
        "objectType": "blob",
        "schedule": "weekly",
        "schemaFields": [
          "Name", "Content-Length", "AccessTier", "Last-Modified",
          "Snapshot", "VersionId", "IsCurrentVersion",
          "Deleted", "RemainingRetentionDays"
        ]
      }
    }
  ]
}

The Snapshot, VersionId and IsCurrentVersion fields are required when you include snapshots and versions. Versioning fields are not available on accounts with a hierarchical namespace, so remove them there. The destination container has to exist first. Apply the rule with the Azure CLI (the command group is still marked preview):

az storage account blob-inventory-policy create \
  -g <rg> --account-name <account> --policy @inventory-policy.json

Inventory is billed per million objects scanned. Snapshots and versions count towards that even if you filter them out of the report. The files themselves are also stored and read at normal rates.

Why the folder breakdown is usually missing

Everything above stops at the account or the container. In practice the question is narrower: which application, customer or folder holds the data, and how much of it is old versions or soft-deleted copies. Blob Storage has no folder-level metric, and Cost Management has no idea what your prefixes mean.

Microsoft's own example query uses Synapse serverless SQL to sum an inventory file per container. Extending it one level down, to container plus first folder, gives a per-prefix view split by tier:

SELECT
    LEFT([Name], CHARINDEX('/', [Name] + '/', CHARINDEX('/', [Name]) + 1) - 1) AS Prefix,
    [AccessTier],
    COUNT(*) AS Objects,
    SUM([Content-Length]) / POWER(1024.0, 3) AS GiB
FROM OPENROWSET(
    BULK '<URL to your inventory CSV file>',
    FORMAT = 'CSV', PARSER_VERSION = '2.0', HEADER_ROW = TRUE
) AS Source
GROUP BY
    LEFT([Name], CHARINDEX('/', [Name] + '/', CHARINDEX('/', [Name]) + 1) - 1),
    [AccessTier]
ORDER BY GiB DESC;

To turn that into money, multiply each row by the capacity price for its tier: monthly_cost(prefix) ≈ Σ GiB(prefix, tier) × capacity_price(tier), with the prices taken from the pricing page for your region and redundancy. Group by the Snapshot, VersionId and Deleted columns too if you want to see how much of each prefix is history rather than live data. Treat the result as an estimate: Content-Length counts the full size of every version, while untiered versions are billed by unique blocks, and Microsoft says inventory totals should not be compared directly with billed capacity. It is good enough to rank prefixes. Large inventories are split into several files listed in the manifest, so query all of them.

If you would rather not maintain that pipeline, Storage Observer scans Azure Blob and ADLS from a daemon that runs next to the storage, and shows which folders use the space, what they cost and how they have grown over time.

Azure Blob Storage lifecycle management policies

Once you know where the data is, lifecycle management handles most of the clean-up. A policy is a JSON document of up to 100 rules. Each rule filters by blob type, by prefix (up to 10, each starting with the container name) or by index tags, and acts on the current version (baseBlob), previous versions (version) or snapshots (snapshot). This example tiers log data down over a year and removes old versions and snapshots across the account:

{
  "rules": [
    {
      "name": "logs-tiering",
      "enabled": true,
      "type": "Lifecycle",
      "definition": {
        "filters": {
          "blobTypes": ["blockBlob"],
          "prefixMatch": ["app-logs/"]
        },
        "actions": {
          "baseBlob": {
            "tierToCool": { "daysAfterModificationGreaterThan": 30 },
            "tierToCold": { "daysAfterModificationGreaterThan": 90 },
            "delete": { "daysAfterModificationGreaterThan": 365 }
          }
        }
      }
    },
    {
      "name": "prune-history",
      "enabled": true,
      "type": "Lifecycle",
      "definition": {
        "filters": { "blobTypes": ["blockBlob"] },
        "actions": {
          "version": { "delete": { "daysAfterCreationGreaterThan": 90 } },
          "snapshot": { "delete": { "daysAfterCreationGreaterThan": 90 } }
        }
      }
    }
  ]
}

The thresholds are spaced so each step comes after the previous tier's minimum: a blob reaches cold 60 days after it went to cool, and is deleted 275 days after it went to cold, so no early deletion charge applies. Apply it with:

az storage account management-policy create \
  --account-name <account> --resource-group <rg> --policy @policy.json

A few points from the policy reference affect cost. The policy is free, but each tier change is billed as a Set Blob Tier operation. A version's age counts from when its data was first written, not from when it became a previous version. The policy will not delete a current version that still has versions or snapshots, which is one reason for the second rule. With soft delete on, lifecycle deletes become soft-deleted and keep billing until retention ends. Changes can take up to 24 hours to apply. Rules that use daysAfterLastAccessTimeGreaterThan need access time tracking, and each last-access update is billed as an "other" operation, at most once per object per day.

A practical next step: enable a weekly inventory rule on your largest storage account today, run the prefix query against the first report, and compare the top ten prefixes with what you expected. That list, together with the meter breakdown in Cost analysis, usually shows which lifecycle rule to write first.
