Resizing an Azure SQL database is one of the easiest ways to buy performance or save money, and Microsoft describes it as having minimal downtime. Minimal is not zero, though. Every change of service tier or compute size ends with a switchover that drops the open connections, and how your application behaves during that moment decides whether anyone notices. This post covers where Azure SQL scaling downtime comes from, how long the whole operation runs, the error numbers your retry logic should handle, and the commands to start, watch and cancel a scale operation. Managed Instance works quite differently and gets its own short section.

What causes Azure SQL scaling downtime

Microsoft's page on scaling single database resources splits the operation into two steps.

First, the service creates a new compute instance with the requested tier and size. For some combinations of source and target, it also has to build a replica of the database on that new compute, which means copying the data. During this step the database stays online and your connections keep going to the original compute, so the application sees nothing except possibly some extra load.

Second, routing switches to the new compute. Existing connections to the old one are dropped, and new connections land on the new one. For some tier changes the database files are detached and reattached at this point. Microsoft says the database is unavailable during the switch "generally for less than 30 seconds and often for only a few seconds". The scale resources overview adds that uncommitted transactions are rolled back when the old engine's connections are terminated.

Two details matter in practice. If long-running transactions are open when connections are dropped, the switch can take longer while those transactions are recovered (accelerated database recovery reduces this, according to the same page). And no data is lost at any point. What you lose is in-flight work: a batch that was halfway through an update, a report query, a connection your pool thought was healthy.

How long a scale operation takes

The short unavailability at the end is only part of the story. The whole operation can run for minutes or hours, depending on whether data has to be copied. Microsoft publishes a latency table on the same scaling page; here is a condensed version.

ChangeLatency modelTypical duration (per Microsoft)
Within Basic or Standard S0–S1Constant, independent of space usedLess than 5 minutes
Within Standard S2–S12 or General Purpose (single database)Constant, independent of space usedLess than 5 minutes
Hyperscale to HyperscaleConstant, independent of space usedLess than 2 minutes
To or from Premium or Business Critical, including Premium to PremiumProportional to space used (data copy)Less than 1 minute per GB used
Between the groups above (for example S1 to S3, or Standard to Hyperscale)Proportional to space used (data copy)Less than 1 minute per GB used

The row that surprises people is Premium and Business Critical. Those tiers keep data on local storage, so moving from one Premium size to another still copies the database. A 300 GB Premium database can take a long time to scale even though only the compute size changes, while a General Purpose database of the same size usually finishes in minutes because its files live on remote storage and are reattached. Moving databases in or out of elastic pools follows similar rules, and Microsoft notes that heavy load during a data copy makes scaling slower, especially on small compute sizes.

Retry logic for transient errors

Microsoft's answer to the switchover is retry logic, and the scaling page explicitly asks you to have it in place before changing the tier. The general guidance in working with transient errors is specific:

  • Wait about 5 seconds before the first retry, then grow the delay exponentially up to a maximum of 60 seconds.
  • If the error happened while connecting, retry the connection.
  • If it happened during a command, do not retry the command on the same connection. Open a fresh connection, then retry.
  • For writes, the retry must make sure the whole transaction either completed or was rolled back.

The error numbers you will see around a switchover are mostly 40613 (database not currently available), 40197 (service error during failover, with a subcode such as 40143 or 40540 embedded), and 4060 (cannot open database, which can be transient while a database is in transition). The Microsoft.Data.SqlClient built-in retry providers page lists the full baseline set the driver treats as transient, including throttling errors such as 40501, 10928, 10929 and 49918, and statement-level errors like deadlocks (1205). Transport errors such as 10054 (connection forcibly closed) are listed as worth adding on top.

Configurable retry logic in Microsoft.Data.SqlClient

Since version 3.0, Microsoft.Data.SqlClient has configurable retry logic. It is off by default, and you enable it by assigning a provider to a SqlConnection, a SqlCommand, or both. The built-in command providers skip retries when the command runs inside a transaction, which is correct but means they do not help much with write paths. A pattern that follows Microsoft's guidance is to let the driver retry opening the connection, and to wrap each unit of work in your own loop that opens a fresh connection and reruns the whole transaction:

using System;
using System.Linq;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Data.SqlClient;

public static class Db
{
    // Setting TransientErrors replaces the driver's built-in list, so include
    // everything you want retried.
    private static readonly int[] TransientErrors =
    {
        64, 233, 4060, 4221, 10053, 10054, 10060, 10928, 10929,
        40143, 40197, 40501, 40540, 40613, 49918, 1205
    };

    private static readonly SqlRetryLogicBaseProvider OpenRetry =
        SqlConfigurableRetryFactory.CreateExponentialRetryProvider(new SqlRetryLogicOption
        {
            NumberOfTries = 6,                          // initial attempt + 5 retries
            DeltaTime = TimeSpan.FromSeconds(5),
            MaxTimeInterval = TimeSpan.FromSeconds(60),
            TransientErrors = TransientErrors
        });

    private static bool IsTransient(SqlException ex) =>
        ex.Errors.Cast<SqlError>().Any(e => TransientErrors.Contains(e.Number));

    public static async Task RunInTransactionAsync(
        string connectionString,
        Func<SqlConnection, SqlTransaction, Task> work,
        CancellationToken ct)
    {
        const int maxAttempts = 5;
        var delay = TimeSpan.FromSeconds(5);

        for (var attempt = 1; ; attempt++)
        {
            try
            {
                await using var conn = new SqlConnection(connectionString);
                conn.RetryLogicProvider = OpenRetry;
                await conn.OpenAsync(ct);

                using var tx = conn.BeginTransaction();
                await work(conn, tx);
                tx.Commit();
                return;
            }
            catch (SqlException ex) when (IsTransient(ex) && attempt < maxAttempts)
            {
                await Task.Delay(delay, ct);
                delay = TimeSpan.FromSeconds(Math.Min(delay.TotalSeconds * 2, 60));
            }
        }
    }
}

Inside work, assign the transaction to every command (cmd.Transaction = tx). A few caveats apply. If the switchover happens exactly while Commit is in flight, you cannot tell from the client whether the transaction committed, so the work itself should be idempotent (an upsert, or a check for an idempotency key) before you retry it blindly. The -2 client timeout is not in the list on purpose; Microsoft's docs point out that the built-in providers do not retry it either, so connection and command timeouts need to be long enough on their own.

Be careful when you combine layers. SqlClient also has idle connection resiliency through the ConnectRetryCount and ConnectRetryInterval connection string keywords, and Microsoft's transient errors page warns that stacking it on top of your own retries multiplies the number of attempts. If you use an ORM or a resilience library, check what it already retries, so that you end up with one retry layer rather than several.

Scaling with T-SQL, Azure CLI and PowerShell

All three methods start the same asynchronous operation and return before the scale is finished. With T-SQL, use ALTER DATABASE. You need to be the server admin, the Microsoft Entra admin, a member of dbmanager in master, or db_owner in the database:

-- DTU model
ALTER DATABASE [mydb] MODIFY (SERVICE_OBJECTIVE = 'S3');

-- vCore model: General Purpose, standard-series (Gen5), 8 vCores
ALTER DATABASE [mydb] MODIFY (SERVICE_OBJECTIVE = 'GP_Gen5_8');

-- Check what the database is running now
SELECT DATABASEPROPERTYEX('mydb', 'Edition')          AS edition,
       DATABASEPROPERTYEX('mydb', 'ServiceObjective') AS service_objective,
       DATABASEPROPERTYEX('mydb', 'MaxSizeInBytes')   AS max_size_bytes;

With the Azure CLI, az sql db update takes either a service objective name or an edition plus capacity. Add --no-wait if you do not want the shell to block until the operation completes:

az sql db update --resource-group "$RG" --server "$SERVER" --name "$DB" \
  --edition Standard --service-objective S3 --no-wait

az sql db update --resource-group "$RG" --server "$SERVER" --name "$DB" \
  --edition GeneralPurpose --family Gen5 --capacity 8 --no-wait

# List operations still running, then cancel one if needed
az sql db op list --resource-group "$RG" --server "$SERVER" --database "$DB" \
  --query "[?state=='InProgress'].name" --output tsv
az sql db op cancel --resource-group "$RG" --server "$SERVER" --database "$DB" --name "$OPERATION"

In PowerShell, Set-AzSqlDatabase does the same, and Get-AzSqlDatabaseActivity and Stop-AzSqlDatabaseActivity list and cancel operations:

Set-AzSqlDatabase -ResourceGroupName $rg -ServerName $server -DatabaseName $db `
  -Edition "Standard" -RequestedServiceObjectiveName "S3" -AsJob

Get-AzSqlDatabaseActivity -ResourceGroupName $rg -ServerName $server -DatabaseName $db

Checking progress with sys.dm_operation_status

From inside SQL, connect to master as a server-level principal and query sys.dm_operation_status:

SELECT operation, state_desc, percent_complete, start_time, last_modify_time, error_desc
FROM sys.dm_operation_status
WHERE major_resource_id = 'mydb'
ORDER BY start_time DESC;

Do not read too much into percent_complete. For a scale operation it is documented as 0, 50 or 100, so it tells you whether the operation has started and finished, not how far along the data copy is. Rows are kept for roughly an hour; for older history use the Azure Activity Log.

When not to scale

The switchover rolls back whatever is running, so avoid scaling during index rebuilds, large imports, long ETL batches or anything else that would have to start over. Schedule scale operations around those jobs, or make the jobs resumable.

To scale down an Azure SQL database, the space it uses must fit within the maximum size of the target. Each service objective has its own maximum data size, listed in the resource limits pages, and the operation fails if the database is bigger. Check used space before planning a downgrade:

SELECT CAST(SUM(CAST(FILEPROPERTY(name, 'SpaceUsed') AS bigint)) * 8 / 1024.0 AS decimal(18, 2)) AS data_space_used_mb
FROM sys.database_files
WHERE type_desc = 'ROWS';

Some other rules from the same page: scaling up does not raise the max size unless you ask for it; with geo-replication you upgrade the secondaries first and downgrade the primary first; downgrading from Premium to Standard can add extra storage charges if the max size is above what the target includes; and moving to Basic shortens backup retention. Databases that use In-Memory OLTP cannot move from Premium or Business Critical to Standard or General Purpose at all.

Billing works per hour. You pay for the highest service objective that applied during each hour, so scaling up for ten minutes costs the same as a full hour at the larger size. If you scale on a schedule, align changes with hour boundaries where you can. To estimate savings, multiply the hours spent at each size by that size's hourly rate from Microsoft's official Azure SQL Database pricing page, and compare the total with the hours you would otherwise spend at the larger size. Use the rate for your own region, since prices vary by region and change over time.

Azure SQL Managed Instance scale-up downtime is a different problem

Managed Instance scaling is a much heavier operation. According to the management operations overview, an update usually resizes or creates a VM group, seeds data where needed, and then fails over to a new engine process. The operation duration page says 95% of vCore scaling operations on General Purpose finish within 60 minutes, and on Business Critical it is 60 minutes plus the time to seed every database to the new replicas (on average about 220 GB per hour). The instance stays available throughout except for the final failover: up to 20 seconds on Business Critical, up to 2 minutes on General Purpose, and on Next-gen General Purpose some databases can take up to 10 minutes to come back when many databases are reattached. Microsoft explicitly advises against scaling while long-running transactions are running. In practice that makes Managed Instance a poor candidate for frequent scheduled scaling; plan resizes like maintenance windows.

Scheduling scale operations

Azure SQL Database autoscale only exists in the serverless compute tier, which adjusts vCores within a range you set and can pause when idle. Whether that or provisioned compute fits better is covered in Azure SQL serverless vs provisioned. For provisioned databases and elastic pools, any automatic scaling is something you build or run yourself, with all the constraints described above.

The usual approach is a scheduled job (an Automation runbook, a Function with a timer trigger, a pipeline) that calls az sql db update or Set-AzSqlDatabase, waits for completion and logs the result. I wrote about automating Azure SQL Database and SQL pool scaling on Medium. If you would rather not maintain that code, our Azure Autoscaler resizes Azure SQL databases and elastic pools on metrics, forecasts or schedules. Whatever runs the schedule, scale up early enough that a data copy finishes before the load arrives, and scale down only after batch jobs are done.

A practical next step

Before you scale anything in production, test what your application does during a switchover. Scale a non-production copy of the database between two objectives while a load test runs, and watch which errors reach your logs and whether any requests fail. If you see 40613 or 40197 surfacing to users, fix the retry path first. Then look up your production database's tier in the latency table, so you know whether a resize will take minutes or will copy every gigabyte.
