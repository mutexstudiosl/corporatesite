Ingress-NGINX retirement on AKS: your migration options

Upstream ingress-nginx stopped receiving fixes in March 2026, and Microsoft's patches for the AKS application routing add-on run through November 2026. This is how we plan the move off it, and why Traefik is where we usually land.

By David García García16 November 202613 min read

If you run AKS clusters, the ingress-nginx retirement probably affects you in one of two ways. Either you installed the community controller yourself with Helm, or you enabled the application routing add-on, which runs a managed NGINX ingress controller. The ingress-nginx retirement on AKS has different deadlines for those two cases, but the work involved is mostly the same: find out what your Ingress objects depend on, pick a replacement, and move traffic without an outage. For most clusters we pick Traefik, and this post explains why, along with the alternatives.

What was retired and what November 2026 means on AKS

In November 2025, Kubernetes SIG Network and the Security Response Committee announced the retirement of Ingress NGINX. Best-effort maintenance continued until March 2026; after that there are no further releases, no bug fixes and no updates for security vulnerabilities. Existing deployments keep working, so nothing breaks on a given day; you are just running an internet-facing proxy that nobody patches any more.

If you installed the open source controller with Helm, that has been your situation since March. If you use the application routing add-on, Microsoft will provide critical security patches for the add-on's NGINX Ingress resources through November 2026, and asks users to migrate before that support ends. In both cases the deadline is now, or very close to it.

The Kubernetes announcement suggests a quick check for whether a cluster runs the controller at all:

kubectl get pods --all-namespaces --selector app.kubernetes.io/name=ingress-nginx

Find out what you are actually using

Before comparing replacements, collect three things: which controllers and IngressClasses exist, which Ingress objects use them, and which nginx annotations those objects rely on. The annotation list decides most of the migration effort.

Start with the classes and controllers. On clusters with the application routing add-on, each NginxIngressController has its own class and its own load balancer IP, and the default one uses webapprouting.kubernetes.azure.com:

kubectl get ingressclass
kubectl get nginxingresscontrollers -o custom-columns=NAME:.metadata.name,CLASS:.spec.ingressClassName

Then list every Ingress with its class. Older objects may still use the kubernetes.io/ingress.class annotation instead of spec.ingressClassName, so check both:

kubectl get ingress -A -o json | jq -r '.items[] |
  [.metadata.namespace, .metadata.name,
   (.spec.ingressClassName // .metadata.annotations["kubernetes.io/ingress.class"] // "<none>"),
   ([.spec.rules[]?.host] | join(","))] | @tsv' | column -t

Now count the nginx annotations across the cluster. This gives you a short list of behaviours you have to reproduce somewhere else:

kubectl get ingress -A -o json \
  | jq -r '.items[].metadata.annotations // {} | keys[]
           | select(startswith("nginx.ingress.kubernetes.io/"))' \
  | sort | uniq -c | sort -rn

Finally, find the objects that use snippet annotations:

kubectl get ingress -A -o json | jq -r '.items[]
  | select((.metadata.annotations // {}) | keys | any(endswith("-snippet")))
  | "\(.metadata.namespace)/\(.metadata.name)"'

Snippets (configuration-snippet, server-snippet and friends) are the hard part. They inject raw NGINX directives, and no other proxy can translate arbitrary NGINX configuration (the Kubernetes announcement also names them as a serious security flaw). Plan to read each snippet, work out what it was meant to do, and rebuild that intent on the new controller. Also look at the controller-wide ConfigMap (for a Helm install with the default release name it is ingress-nginx-controller in the ingress-nginx namespace), since global settings there change behaviour for every Ingress.

The options after the ingress-nginx retirement on AKS

Traefik (our recommendation for most clusters)

We run Traefik on production AKS clusters, and it is the replacement we reach for first. The main reason is that it meets you where your manifests already are. Traefik v3.6.2 and later includes a Kubernetes Ingress NGINX provider. It reads your existing Ingress objects (by default those whose IngressClass has the controller k8s.io/ingress-nginx) and translates many nginx.ingress.kubernetes.io annotations, including auth, CORS, canary, rate limiting, timeouts, buffering and a limited set of directives inside configuration-snippet and server-snippet. You can install Traefik next to ingress-nginx, point it at the same objects and test it without rewriting manifests. With the Helm chart, enabling the provider looks like this:

helm repo add traefik https://traefik.github.io/charts
helm repo update
helm upgrade --install traefik traefik/traefik \
  --namespace traefik --create-namespace \
  --set providers.kubernetesIngressNGINX.enabled=true

Once traffic has moved, you are not stuck with nginx annotations. The same Traefik deployment also implements the standard Ingress API, Gateway API, and its own CRDs (IngressRoute and Middleware), so you can move route by route at your own pace. Middleware objects cover things Gateway API has no standard field for, such as rate limiting, IP allow lists, forward auth and header manipulation, and when the built-in set is not enough there is a plugin mechanism for custom middleware.

Traefik runs inside the cluster and watches Ingress, Gateway API and its own CRDs through the Kubernetes API, then rebuilds its routing table in-process. There is no external service to program in between. In our experience a changed Ingress, HTTPRoute or Middleware is live on Traefik faster than the same change on Application Gateway for Containers, which has to go through Azure (more on that below).

It also fits the rest of the Kubernetes tooling you probably already run. TLS certificates are ordinary kubernetes.io/tls Secrets referenced from spec.tls or a Gateway listener, so cert-manager works the normal way, either with ingress annotations or with its Gateway API support. ExternalDNS can read the published addresses from Ingress status or Gateway resources, and because the configuration is plain Kubernetes objects, GitOps tools manage it like anything else in the cluster. The Service in front of Traefik is a regular Azure Load Balancer, so you keep a static public IP if your firewall rules or upstream services need one.

The trade-off is that you operate it yourself, and it is not a Microsoft-supported component. Upgrades, scaling and monitoring are your job. The provider also has documented differences from ingress-nginx: only round-robin load balancing, only persistent session affinity, forward auth without session caching, and rate limiting that returns 429 rather than 503. The reference has a long table of unsupported annotations, among them enable-modsecurity, global-rate-limit and mirror-target. Compare your annotation count from the inventory against that table before you commit.

AKS application routing with Gateway API

This is the successor Microsoft points to, and it is a reasonable choice if your Ingress objects are plain host and path routing with TLS and you want AKS to manage the controller. The application routing Gateway API implementation deploys a lightweight Istio control plane that only reconciles Gateway API resources for the approuting-istio GatewayClass. It does not support sidecar injection or Istio CRDs. Each Gateway gets its own Envoy deployment, Service, HorizontalPodAutoscaler and PodDisruptionBudget, and the control plane is upgraded in place with the cluster. You enable it with the managed Gateway API CRDs (Azure CLI 2.86.0 or later):

az aks update --resource-group $RG --name $CLUSTER --enable-gateway-api --enable-app-routing-istio
kubectl get gatewayclass approuting-istio

Check the limitations first: you cannot configure request header and body size limits, Lua scripts, or local and global rate limiting, and EnvoyFilter is not supported. It also cannot run at the same time as the Istio service mesh add-on. If you need those features, Microsoft suggests Gateway API ingress with the Istio service mesh add-on, which allows a gateway-scoped EnvoyFilter; the trade-off is that EnvoyFilter issues are outside Azure support and you have to run canary upgrades for minor Istio versions yourself. There is no translation layer for nginx annotations either, so every Ingress has to be rewritten as Gateway API resources before it can move.

Application Gateway for Containers

Application Gateway for Containers is Microsoft's managed layer 7 load balancer for AKS. Azure operates the data plane outside the cluster. An ALB Controller inside the cluster watches Ingress, Gateway, HTTPRoute and its own custom resources, and applies that configuration to the gateway in Azure. It supports the Ingress API and Gateway API, WAF policies, mTLS, header and URL rewrites, JWT validation, traffic splitting and several load balancing algorithms. Gateway listeners only allow ports 80 and 443, the service is available in a specific list of regions, and each frontend is reached through an Azure-generated FQDN that you point a CNAME at rather than a static IP. Each deployment also needs a delegated subnet; Microsoft's components page asks for at least a /24 per association.

We have run it in production, and for most clusters we would not choose it again. These are the reasons.

It ties your ingress to Azure. The data plane is an Azure resource, not a controller you can deploy elsewhere. Your HTTPRoutes may be standard Gateway API, but the GatewayClass, the alb.networking.azure.io annotations, the ApplicationLoadBalancer resource, frontends, associations and security policies are all Azure-specific. If a workload later moves off AKS, you replace the ingress layer rather than take it with you. Traefik runs the same way on any Kubernetes cluster.

Configuration changes take a longer path. The components page describes how the ALB Controller "uses both ARM and Application Gateway for Containers configuration APIs to propagate configuration" to the Azure deployment, and it needs outbound access to Azure Resource Manager, Entra ID and the configuration endpoint to do it. A route is only live when its status reports that the Application Gateway for Containers resource has been updated and the condition is Programmed. Microsoft does not publish a propagation time. Architecturally it is a remote call to a managed service, where Traefik applies the change in the same process that serves traffic, and in our experience Traefik picks up Ingress, Gateway and Middleware changes noticeably faster. When something goes wrong in that chain, such as a missing role assignment or federated credential, the troubleshooting guide shows the symptom as routes that simply stop being applied while the controller retries.

It is another Azure bill and another set of resources. Application Gateway for Containers is billed as its own Azure resource on top of the cluster, and WAF adds to that. Microsoft lists it on the Application Gateway pricing page. You also need a managed identity with the AppGw for Containers Configuration Manager role and the delegated subnet mentioned above. Traefik runs on nodes you already pay for, behind the standard load balancer AKS already creates.

The feature set is fixed. What Application Gateway for Containers can do is the list in Microsoft's overview: routing on host, path, header, query string and method, rewrites and redirects, retries, health probes, mTLS, JWT validation, WAF and so on. That list is decent, but if you need something outside it you wait for Azure to add it. There is no equivalent of Traefik's Middleware chain or plugin mechanism, and snippet-style customisation from ingress-nginx has nowhere to go.

Certificates must live in the cluster, and Key Vault mounting is not supported. To be fair here: cert-manager does work. Microsoft documents cert-manager with Let's Encrypt on Gateway API, and the SSL offloading guide states that certificates must be stored as Kubernetes secrets. The same note says Azure Key Vault integration through the Secrets Store CSI driver is not supported, because the gateway cannot mount certificates from external volumes. If your current setup on the application routing add-on pulls certificates from Key Vault, plan to replace that flow with cert-manager or another way of syncing Secrets. On Traefik you would end up with the same Secret-based setup, so this point is less about Traefik being better and more about Application Gateway for Containers removing an Azure-native option you might expect it to have.

If you are fully committed to Azure, want Microsoft to run the data plane and need nothing beyond its feature list, it can still be a sensible choice. We would not start there.

Other Gateway API implementations

Any conformant Gateway API implementation (Envoy Gateway, kgateway, Cilium and others) can work on AKS if you are prepared to run it yourself. The upstream guide for ingress-nginx users recommends starting with ingress2gateway, which converts Ingress objects and ingress-nginx annotations into Gateway API resources and warns about what it could not translate. The tool is also useful if you start on Traefik's ingress-nginx provider and later move routes to Gateway API. On application routing clusters, pass the class explicitly, since the tool reads class nginx by default:

ingress2gateway print --providers=ingress-nginx \
  --ingress-nginx-ingress-class=webapprouting.kubernetes.azure.com -A

Treat the output as a first draft. Experimental fields such as URLRewrite are only emitted with --allow-experimental-gw-api.

Run both controllers and cut over with DNS

Every option above gets its own address, so the safe pattern is the same for all of them. Microsoft's add-on migration guide and Traefik's NGINX migration guide both describe a variant of it:

  1. Inventory hostnames and anything upstream that pins the current IP: Front Door origins, Traffic Manager endpoints, firewall allow lists.
  2. Install the new controller alongside ingress-nginx and create the routes (or let Traefik read the existing Ingress objects).
  3. Lower the DNS TTL for the affected records and wait for the old TTL to expire.
  4. Test the new IP directly before touching DNS, for every host and path, including HTTPS with the real certificate.
  5. Point DNS (and the upstream references) at the new IP, and watch request rates on ingress-nginx fall to zero.
  6. Keep ingress-nginx running for a while as a rollback path, then remove it and raise the TTL again.

For step 4, curl --resolve lets you pin a hostname to the new address without changing DNS:

curl -sS -o /dev/null -w '%{http_code}\n' \
  --resolve "app.example.com:443:${NEW_IP}" https://app.example.com/

You cannot move the existing ingress-nginx public IP to the new Service in place. Microsoft's guide explains that AKS deletes its managed public IPs when the owning Service is removed, even if they are marked Static, which is why both guides change DNS and upstream references instead.

Things that commonly break

Annotations without an equivalent. Gateway API has no standard fields for body size limits or rate limiting, so on the app routing implementation those features simply disappear unless you choose a different option. Run your annotation count against the target before committing.

Defaults. ingress-nginx uses a 1 MB body size limit and 60 second proxy timeouts by default, and buffers request bodies. Traefik's ingress-nginx provider keeps the same size and timeout defaults but turns request buffering off, and it expects sizes in bytes and timeouts in integer seconds rather than 1m or 60s. Upload endpoints and slow backends are where differences show up first.

Regex paths and rewrites. With Traefik's default strictValidatePathType: true, an Ingress is rejected entirely if a path contains regex characters while its pathType is Prefix or Exact, which is common with use-regex. Traefik also notes that with rewrite-target plus auth annotations, the auth request sees the rewritten path.

Client IP. If you use externalTrafficPolicy: Local to keep the real client address, carry it over. The app routing Gateway API implementation adds Azure Load Balancer health probe annotations for the default Cluster policy, and you must unset them if you switch the Gateway Service to Local. IP allow lists depend on this: Traefik's whitelist-source-range uses the remote address of the request unless you configure ipAllowListStrategy.

TLS and certificates. HTTP-01 ACME challenges cannot succeed against a controller that is not yet receiving public traffic, so during the parallel phase use the existing spec.tls secrets or DNS-01 validation. On the app routing implementation, Key Vault certificates are wired differently from the NGINX add-on and need their own setup step.

Ingress status. When two controllers watch the same Ingress, both write status.loadBalancer, and ExternalDNS or GitOps tools may see the address flap. Traefik documents disabling its publishService during coexistence, or using a transitional IngressClass.

WAF and CrowdSec middleware on Traefik

ingress-nginx can switch on ModSecurity per Ingress with the enable-modsecurity annotation, and that annotation is on Traefik's unsupported list. On Traefik the usual route is a community plugin for ModSecurity or CrowdSec, attached to routes as a Middleware like any other. Those plugins run inside the Yaegi Go interpreter on every request. A Traefik issue about compiling middlewares into the binary describes memory and CPU problems with interpreted middleware on busy routes; it was closed without being added to the roadmap. Building the middleware into the binary avoids the interpreter. That is what our Traefork does: it is a soft-fork that stays in sync with upstream Traefik and compiles ModSecurity, Geoblock, RealIP, CrowdSec and Sablier into the binary. It is not affiliated with Traefik Labs.

A practical next step

Run the inventory commands on each cluster and keep the output. The annotation counts and the snippet list usually make the choice for you. A long tail of nginx annotations makes Traefik's ingress-nginx provider the quickest way off an unpatched controller, and it leaves room to move to Gateway API later. A WAF or CrowdSec requirement is also something we would handle on Traefik, with plugin middleware or a build that compiles it in. If all you have is plain host and path routing and you would rather AKS managed the controller, the app routing Gateway API implementation is the Microsoft-supported route.
